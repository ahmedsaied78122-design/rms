# مراجعة Streaming بين الماستر وجهاز سعيد — 2026-11-16

تم إصلاح المشاكل في Arab Streaming الأساسي أولًا، ثم نشر المحرك وتعديلات RMS
على GitHub وتنزيلها على جهاز سعيد. مسارات التشغيل الموضحة أدناه نجحت على الموقعين.
هذا التقرير يميز بين التجربة الفعلية، وفحص الحقول، والحالات التي لم تُجرّب عمليًا.

## الإصلاحات التي نُشرت

- إضافة مزامنة الباسورد المشفرة والموجهة للمستقبل، مع كشف تغييرات Auth التي لا تعمل User.save.
- إضافة تفعيل مستقل على الجهازين لباسورد Administrator، بدون مزامنة ملفه أو أدواره أو API keys.
- منع تشغيل فرع مربوط بسليف من POS الماستر، حتى عند توقف النقل مؤقتًا.
- تقسيم أسماء المستندات بحسب الفرع والجهاز، بما فيها POS Opening/Closing التي تستخدم سلسلة ثابتة.
- التقاط db_set، وإشعار النقل بعد تحديثات SQL الخاصة بملاحظة سطر الطلب وإقرار إلغاء المطبخ.
- إصلاح توجيه POS Profile المشترك، وصلاحيات المستندات المستقبلة، وإبطال cache الصلاحيات بعد commit.
- منع صدى Contact الذي ينشئه User job، ومعالجة اختلاف أسماء صفوف الهاتف المتطابقة فعليًا.
- إبقاء tax-breakup HTML محليًا، ومعالجة حالات الفواتير والتجميع بعد الاعتماد بدون تجاوز حماية القيم المالية.
- إضافة Stock Entry Type وحقل الاسم العربي المرجعي إلى إعداد السليف.
- السماح بإكمال المطبخ بعد الدفع دون إعادة فتح الطلب المدفوع.
- إلغاء حركة الهالك الأصلية داخل إلغاء مستنده، مع تحقق المحرك من حدث الإلغاء الأصلي والـbase والربط والصلاحيات.

## الباسورد والأدمن

قاعدة User مفعّل فيها Include Passwords. كما فُعّل على الموقعين:

```json
{"arab_streaming_sync_administrator_password": 1}
```

التغيير من الماستر يتجه للسليف. يمكن استخدام باسورد Administrator الحالي على
الماستر لتسجيل الدخول على السليف. وصول باسورد جديد ينهي جلسات المستخدم على السليف.
Guest وحسابات التكامل مستثناة. API keys وأسرار الربط لا تتغير.
المسار لا يجعل تعديل باسورد السليف تغييرًا لباسورد الماستر؛ التغيير المركزي يتم من الماستر.

## الحسابات والمخزون وتنظيف الاختبار

تمت مقارنة 11 مستندًا ماليًا/مخزنيًا تجريبيًا. قيود GL متطابقة على مستوى الحسابات
والمبالغ والعملات والأبعاد المشتركة، مع صفر رصيد صافٍ غير ملغى للاختبار على كل حساب.
كمية وقيمة مخزون صنفي الاختبار صفر على الجهازين. لا توجد Capture أو Dispatch
بحالة Pending/Failed نشطة وقت الفحص النهائي.

هناك فرق تاريخي واحد في `qty_after_transaction` لصف SLE **ملغى** من حركة الهالك
الأولى قبل الإصلاح: إلغاء الاستلام وصل قبل اكتمال عكس الهالك على الماستر. كميات
وقيم الحركة وقيودها وحالة الإلغاء والرصيد النهائي متطابقة. لم تُعدّل صفوف الـledger
يدويًا. الدورة الجديدة بعد الإصلاح اجتازت المقارنة الكاملة.

تم تعطيل مستخدم الاختبار وPOS User وPOS Profile والعميل والصنف والمنتج وUOM
التجريبيين، وتأكد وصول التعطيل للسليف. أُبقيت مستندات الاختبار الأصلية وعكسها
وسجلات أخطائها القديمة المؤرشفة للمراجعة؛ لم تُحذف حركات محاسبية أو تاريخ فعلي.

## تغطية الحقول وحدود النتائج

- قواعد النقل النشطة: 59 DocType أساسيًا.
- مع الجداول التابعة: 152 مسارًا، و2692 حقل metadata.
- 1891 حقلًا قابلًا للنقل اجتاز اختبار codec/JSON؛ صفر فشل في هذا الفحص.
- بقية الحقول مصنفة محلية أو عرض أو مستثناة. ملف CSV يوضح كل حقل ونوعه ونتيجته.
- الاختبارات: مجموعة المحرك الكاملة 138 ناجحًا، ثم مجموعة الباسورد النهائية 11 ناجحًا بعد إضافة تهيئة المستقبل؛ مجموعة RMS المركزة 167 ناجحًا. هذه أعداد مجموعات، وليست مجموعًا لاختبارات مستقلة بلا تكرار.

فحص codec لا يعني تعديل كل حقل منفردًا وحفظه على المواقع الحية. المقارنة الخام
للسجلات لا تُفسّر وحدها كفشل نقل: توجد روابط صور أُعيدت كتابتها مع محتوى مطابق،
وأسماء صفوف تابعة، وقيم مشتقة محليًا مثل تكلفة الوصفة من تقييم مخزون الموقع،
وعملة حساب فارغة تُطبّع للعملة الافتراضية، وملخصات المستخدم والمبيعات. كما أبقت
سياسة النسخ الأولى Skip بعض التعريفات والمستخدمين الموجودين مسبقًا، والعمليات
التاريخية للماستر لا تُنسخ نزولًا لأنها Slave-to-Master. الحسابات المضمنة وإضافات
HR/Lending/حقول POS قديمة على الماستر خارج حزمة السليف ذات التطبيقات الأربعة.
هذه ليست شهادة بأن كل قيمة في قاعدة البيانات متطابقة.

لم تُجرّب حيًا كل تركيبات modifiers/recipes والخصومات وOTP والمرتجعات الجزئية
والنقل والتقسيم والدمج، ولا صرف Shift Expense فعلي، ولا تحميل 38 سليفًا معًا، ولا
تثبيت جهاز ثالث من الصفر في هذه الجولة. لا يُدّعى اعتماد شامل لكل هذه الحالات.
